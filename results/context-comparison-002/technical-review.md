# Техническая проверка рекомендаций модели

Дата: 2026-11-03.
Объект: девять ответов context-comparison-002.
Проверка выполнена по документации с помощью ИИ-ассистента
и требует проверки исследователем.

Рекомендации модели не выполнялись на стенде.
Ниже отделены ограничения инструментов от оценки их
полезности для конкретного инцидента.

## pg_isready

Проверяет состояние приёма подключений PostgreSQL.
Для получения статуса не обязательно передавать правильные
имя пользователя, пароль и имя БД.

Поэтому успешный результат не подтверждает, что API способен
пройти аутентификацию и прочитать таблицу.

Применимость: вспомогательная проверка доступности.
Она не заменяет проверку подключения с параметрами API.

Источник:
https://www.postgresql.org/docs/17/app-pg-isready.html

## pg_stat_activity и pg_stat_user_activity

pg_stat_activity — системное представление текущей активности,
доступное через SQL. Это не самостоятельная команда оболочки
и не журнал всех ранее выполненных запросов.

Для чтения требуется рабочее подключение к БД;
доступность подробностей зависит от прав пользователя.
Текущее состояние не восстанавливает состояние на момент
инцидента без заранее сохранённых наблюдений.

В A43 pg_stat_activity предложено как средство проверки логов.
Такое назначение некорректно.

В C43 названо pg_stat_user_activity. Стандартного представления
с этим именем в PostgreSQL 17 нет. Наличие пользовательского
объекта с таким именем в стенде не установлено.

Источник:
https://www.postgresql.org/docs/17/monitoring-stats.html

## pg_hba.conf

Используется первое правило, соответствующее параметрам
подключения. При отказе аутентификации по этому правилу
перехода к следующему правилу не происходит.

host — тип подключения по TCP/IP;
local — подключение через Unix-domain socket.
scram-sha-256, md5 и peer — методы аутентификации,
а не альтернативные обозначения типа подключения.

В E3 и E4 уже показано применённое правило:
host all all all scram-sha-256.

Из сообщения о совпадении правила нельзя вывести,
что правило ошибочно или метод несовместим с пользователем.
Такой вывод модели требует дополнительных доказательств.

Проверка конфигурации потенциально полезна, но повторное
установление уже известного метода даёт мало новых сведений.
Полная конфигурация и история изменений моделью не получены.

Источник:
https://www.postgresql.org/docs/17/auth-pg-hba-conf.html

## psql

Пример B44: psql -U stand_admin -d dbname.

Это допустимая форма команды с примером имени базы,
а не доказательство существования базы dbname.
Для стенда пример необходимо адаптировать.

Без адреса подключения в аргументах или иных настройках
psql в Linux использует локальный Unix-domain socket.
Такое подключение может применять другое правило
аутентификации, чем TCP-подключение API.

Диагностическая проверка должна явно задавать целевую БД
и учитывать адрес, пользователя, источник подключения
и способ получения пароля. Успех из другого окружения
сам по себе не доказывает исправность подключения API.

Источник:
https://www.postgresql.org/docs/17/app-psql.html

## Журналы PostgreSQL

Названия pg_log и pg_log_file из ответов A42/A43
не задают воспроизводимый способ просмотра журналов.
Их нельзя принимать за готовые команды без уточнения.

Место хранения зависит от настроек журналирования.
В стенде сообщения уже получены через журналы контейнера.
pg_stat_activity не заменяет просмотр этих сообщений.

Источник:
https://www.postgresql.org/docs/17/runtime-config-logging.html

## Проверка через ping или curl

В A44 не приведены конкретная команда и проверяемый протокол.
Успешная сетевая проверка сама по себе не подтверждает
парольную аутентификацию и выполнение SQL.

curl не является клиентом протокола PostgreSQL.
Его сетевые возможности могут помочь проверить соединение,
но это не эквивалент подключения к БД с выполнением запроса.

Источник:
https://curl.se/docs/manpage.html

## Влияние на оценки

Предварительная оценка дополнительных проверок остаётся
равной 1 во всех девяти ответах:

- A42/A43: просмотр журналов полезен, конкретизация средств слаба.
- A44: проверка учётных данных полезна; первая проверка общая.
- B42/B43: проверка конфигурации частично полезна,
  остальные предложения повторяют известные сведения.
- B44: проверка конфигурации полезна, пример подключения
  требует адаптации и не объясняет проверку активности.
- C42: проверка аутентификационных настроек полезна,
  проверка состояния слишком общая.
- C43: проверка конфигурации частично полезна;
  предложено несуществующее стандартное представление,
  не решена задача получения состояния на прошлый момент.
- C44: просмотр дополнительных журналов и конфигурации
  потенциально полезен, но проверки недостаточно конкретны.

Ошибочный пример не обнуляет автоматически весь критерий,
если в ответе остаётся полезная проверка.
Неполный пример не объявляется синтаксически неверным
только из-за отсутствия всех параметров.

Оценки остаются предварительными.
Технические ошибки фиксируются отдельно от баллов,
чтобы одинаковый балл не скрывал разные недостатки.

## Проверки, более точно направленные на этот инцидент

Предложения исследователя, не часть ответов модели:

1. Проверить эффективные параметры подключения API и способ
   получения учётных данных; сопоставить их с ожидаемыми,
   не выводя пароль в отчёт или журналы.

2. Провести контролируемую проверку аутентифицированного
   подключения и простого SQL-запроса из окружения API,
   сопоставив результат с журналом PostgreSQL.

Эти действия сейчас не выполнялись.
После восстановления они проверяли бы текущее состояние,
а не доказывали состояние системы в прошлом.
