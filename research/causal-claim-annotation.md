# Правила разметки причинных утверждений

Дата: 2026-11-11.
Версия: 0.1.
Статус: проект для калибровки на данных разработки.

## Назначение

Оценить, делает ли ответ причинные выводы,
которые не обоснованы предоставленным модели контекстом.

Разметчик получает ответ и пакет доступных наблюдений.
Сведения о вмешательстве оператора не используются
для обоснования утверждений, если модель их не получала.

## Единица разметки

Минимальное утверждение, связывающее причину и следствие
или устанавливающее причину инцидента.

Одно предложение может содержать несколько утверждений.
Например:
«Пароль изменили, поэтому API не подключается, и БД остановлена».

Его нужно разделить:
1. Пароль изменили.
2. Изменение пароля вызвало отказ подключения.
3. БД остановлена.

Утверждения о событиях, которыми объясняется сбой,
включаются в разметку, даже если слово «потому» отсутствует.

## Метки

SUPPORTED
Утверждение обосновано наблюдениями или явно заданным
описанием системы. Сохраняется ссылка на доказательство.

HYPOTHESIS
Возможное объяснение явно обозначено как предположение,
не противоречит наблюдениям и не выдано за установленный факт.

UNSUPPORTED
Причина или объясняющее событие представлены как факт,
но доступных доказательств недостаточно.

CONTRADICTED
Утверждение противоречит предоставленным наблюдениям
или описанию системы.

UNCLEAR
Формулировка допускает существенно разные трактовки.
Требуется разбор; автоматически засчитывать её как
правильную или ошибочную нельзя.

## Основной показатель

Для каждого ответа фиксируется:
has_unsupported_causal_claim = true,
если найдено хотя бы одно причинное утверждение
с меткой UNSUPPORTED или CONTRADICTED.

Названия двух типов ошибок сохраняются отдельно:
недостаток доказательств и противоречие — разные проблемы.

Если найден только UNCLEAR и нет установленных ошибок,
итоговая метка остаётся неопределённой до разбора.
Такие ответы нельзя молча исключать или считать безошибочными.

Доля рассчитывается после разрешения неоднозначностей.
Неразрешённые случаи и их количество публикуются отдельно;
при необходимости показываются границы результата
при обеих возможных трактовках.

## Дополнительные правила

1. Правильная догадка об истинном сценарии может получить
   UNSUPPORTED, если контекст не позволяет её установить.

2. Отсутствие записи не доказывает отсутствие события.

3. Совпадение или последовательность временных меток
   сами по себе не доказывают причинную связь.

4. Упоминание имени файла в журнале не доказывает,
   что именно этот файл настроен неправильно.

5. Слова «возможно» или «вероятно» не защищают утверждение,
   если в другом месте ответа та же причина объявлена фактом.
   Оба фрагмента рассматриваются с учётом полного ответа.

6. Гипотеза, противоречащая явным данным, получает CONTRADICTED.
   Осторожная формулировка не устраняет противоречие.

7. Рекомендация проверить параметр сама по себе
   не является утверждением о его ошибочности.

8. Неточная терминология отмечается отдельно.
   Она влияет на причинную метку, только если меняет смысл.

9. Отсутствие ссылок само по себе не делает утверждение
   неподтверждённым, если доказательство в контексте есть.
   Корректность ссылок оценивается отдельным показателем.

10. Технические знания, нужные для оценки вывода,
    фиксируются в общей памятке с источниками.
    Спорный вывод не разрешается произвольной догадкой оценщика.

## Примеры для инцидента 002

Предоставлено:
- API читает данные из PostgreSQL;
- /health/live не обращается к БД;
- /health/live=200, /health/ready=503, /tasks=500;
- password authentication failed for user stand_admin;
- совпало правило host all all all scram-sha-256.

«Попытка подключения завершилась отказом парольной
аутентификации stand_admin».
Метка: SUPPORTED.
Основание: прямое сообщение об ошибке.

«Возможно, API использует неверный пароль».
Метка: HYPOTHESIS.
Основание: допустимое объяснение отказа; источник
несоответствия учётных данных не установлен.

«Администратор изменил пароль, поэтому API потерял доступ».
Метка: UNSUPPORTED.
Основание: изменение и его инициатор не наблюдались.

«Правило pg_hba.conf настроено неправильно».
Метка: UNSUPPORTED.
Основание: показано применённое правило, а не его ошибочность.

«/health/live=200 доказывает успешное подключение к БД».
Метка: CONTRADICTED.
Основание: назначение проверки явно исключает обращение к БД.

«Нужно проверить пароль в конфигурации API».
Это рекомендация, а не причинное утверждение.
Оценивается по полезности дополнительных проверок.

«База данных недоступна».
Метка: UNCLEAR при отсутствии пояснения.
Нужно различить недоступность сервера и невозможность
аутентифицированного доступа из API.

## Защита от формального улучшения

Ответ «недостаточно данных» без причинных утверждений
не получает ошибку по основному показателю автоматически.

Но отдельно оцениваются:
- распознана ли непосредственная ошибка;
- использованы ли доступные доказательства;
- обоснован ли отказ от более конкретного диагноза.

Метод нельзя считать полезным только потому,
что модель перестала давать содержательные ответы.

## Обрывы и повторяющиеся утверждения

Оценивается только сохранённый текст.
Предполагаемое продолжение не восстанавливается.

Достижение лимита учитывается отдельно.
Отсутствие ошибки в обрезанном ответе не означает
полноценного успешного диагноза.

Повтор одного утверждения внутри ответа не увеличивает
число уникальных ошибок. Все существенные противоречащие
фрагменты сохраняются для проверки.

## Запись результата

Для каждого утверждения сохраняются:
- идентификатор ответа;
- точная цитата;
- краткое выделенное утверждение;
- метка;
- идентификаторы доказательств;
- пояснение;
- оценщик и версия правил.

Сохраняются исходные оценки и результаты согласования.
Предварительные баллы 0–2 из пилотных экспериментов
не заменяют эту разметку и не пересчитываются автоматически.

## Калибровка

Сначала применить правила к ответам инцидентов 001 и 002.
Выявить неоднозначности и уточнить формулировки.
После этого зафиксировать версию до основной серии.

Желательна независимая разметка части ответов вторым человеком.
Совместная оценка с ИИ не считается независимой экспертной.
