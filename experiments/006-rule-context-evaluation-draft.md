# Проверка диагностических правил в контексте локальной модели

Дата: 2026-11-13.
Статус: проект до технической проверки сценариев; не объявляется зарегистрированным основным экспериментом.
Базовая версия реализации: fd58091, ветка feature/experiment-stand.
Подготовлено совместно с ИИ-ассистентом; требуется проверка исследователем.

## 1. Вопрос исследования и границы

Уменьшает ли добавление детерминированного диагностического блока
неподтверждённые причинные утверждения локальной модели при сохранении
точности распознавания непосредственной ошибки?

Дополнительный вопрос: даёт ли модель полезные сведения и проверки сверх
результата самих правил?

Исследуется добавление внешних знаний правил к одному и тому же набору
наблюдений. Это не сравнение только форматов текста. Временной аудит,
описание системы, вопросы и исходные наблюдения одинаковы для парных условий.
Эффект времени получения, полноты источников и строгой фильтрации
по отдельности данным экспериментом не проверяется.

Инциденты 001–003, прежние генерации и ручная калибровка относятся к разработке.
Новые случаи используют знакомые классы ошибок на том же стенде.
Не заявляется переносимость на неизвестные классы отказов или промышленные системы.

## 2. Предлагаемые случаи

| ID | Вмешательство для оператора | Диагностическая задача |
|---|---|---|
| C01 | Неверный пароль в подключении API к отдельной тестовой роли | Определить отказ аутентификации, не объявляя конкретное место изменения установленным |
| C02 | Изменение пароля отдельной тестовой роли при прежнем пароле API | Та же категория наблюдаемой ошибки при другом вмешательстве |
| C03 | API подключён к отдельной существующей базе без целевой таблицы | Отличить сообщение об отсутствующем отношении от доказанного удаления таблицы |
| C04 | Таблица существует, но схема исключена из search_path подключения API | Та же категория ошибки разрешения отношения при другой причине |
| C05 | API использует отдельную роль без SELECT на целевую таблицу | Определить отказ прав, не утверждать, что права обязательно были отозваны |
| C06 | Неверное имя узла в конфигурации подключения API | Определить ошибку разрешения имени, не утверждать остановку БД |

Это предварительная матрица: точные команды подготовки, вмешательства и
восстановления фиксируются до генераций. Для C01/C02 возможна неразличимость
причин по доступному пакету; аналогично для C03/C04. Она не считается недостатком
данных, который следует устранять раскрытием действий оператора.

Разрешается предварительно проверить техническую осуществимость без запуска LLM.
Если случай не воспроизводится или появляется другой тип ошибки, он получает
статус неуспешной подготовки, а не подменяется молча. Матрица и протокол
уточняются отдельным коммитом до просмотра новых ответов.

Не менять пароль stand_admin, не удалять таблицу production_tasks и её данные.
Для новых ролей/баз использовать выделенные тестовые имена. Для каждого
вмешательства заранее подготовить восстановление и проверить исходное состояние.

## 3. Сбор и сохранение данных

Для каждого случая сохранить:

- код и конфигурацию стенда, исходное состояние, действия оператора;
- HTTP-проверки live/ready/tasks до отказа, при отказе и после восстановления;
- тела, заголовки, stderr, коды curl и время завершения получения;
- журналы API/БД до восстановления, коды и stderr выгрузок;
- фактическую границу диагностики и наблюдаемое разрешение временных меток;
- результат восстановления; хеши всех материалов.

Модель получает только описание системы, согласованные наблюдения до восстановления,
ограничения данных и вопросы. Действия оператора, секреты, сведения о восстановлении,
имена сценариев с подсказкой причины и эталонный диагноз в запрос не включаются.
Один и тот же пакет используется для R, L0 и L1. Выбор строк нельзя менять по ответам.
Для каждого случая заранее сохраняется явное описание отбора данных; желательно
сохранять все полученные строки за одинаково определённое окно наблюдения.

Используется режим аудита без фильтрации. Неизвестное время получения не выдумывается;
совпадение с исключающей границей не исправляется задним числом. Неуспешные
выгрузки и временные ограничения отражаются в материалах и запросах.

## 4. Условия

| Код | Выполнение | Оцениваемый материал |
|---|---|---|
| R | rules-only | Сигнатуры, цитаты, границы вывода, рекомендации правил |
| L0 | with-model, context-mode baseline | Исходный answer.txt модели |
| L1 | with-model, context-mode with-rules | Исходный answer.txt модели |

Объединённый report.md не используется вместо answer.txt при сравнении L0/L1:
он содержит результаты правил даже для L0. Удобство отчёта инженеру здесь не измеряется.

Модель: Qwen/Qwen3-1.7B.
Ревизия: 70d244cc86ccca08cf5af4e1e306ecf908b1ad5e.
dtype=bfloat16; enable_thinking=false.
do_sample=true; temperature=0.7; top_p=0.8; top_k=20.
max_new_tokens=1536; seeds=42,43,44 для обоих модельных условий.
Вопросы: неизменный question_text из зафиксированного входа инцидента 003.

Итого при шести включённых случаях: 6 результатов R и 36 генераций L0/L1.
Одинаковый seed задаёт парный повтор, но не гарантирует идентичную траекторию
генерации при разных запросах или полную межплатформенную воспроизводимость.

Порядок 36 заданий перемешивается заранее с order_seed=20261113 и сохраняется.
Запуски последовательные, на одной конфигурации оборудования и окружения.
Сохраняются версии библиотек, GPU, параметры, исходный и оформленный запрос,
хеши, ответы, время и статусы. Дополнительная длина L1 учитывается как стоимость метода.

## 5. Оценка

Основная метрика L0/L1: наличие хотя бы одного неподтверждённого или противоречащего
данным причинного утверждения в полном ответе.
Применяются research/causal-claim-annotation.md v0.1 и зафиксированная техническая памятка.
Хеши правил и памятки сохраняются до разметки. Полный ответ оценивается, включая
пояснения к рекомендациям; повтор одной причины не увеличивает число уникальных ошибок.

Для каждой метки сохранить точную цитату, ссылку на наблюдения, обоснование и оценщика.
UNCLEAR не считается автоматически правильным или ошибочным. При отсутствии
другой установленной ошибки итог ответа остаётся неопределённым.
Утверждение о действиях оператора может быть верной догадкой, но не считается
обоснованным, если этих действий нельзя установить из предоставленных наблюдений.

Дополнительные показатели:

- Непосредственная ошибка: 2 — точный тип и объект отказа; 1 — общая ошибка
  подключения/доступа без нужного различения; 0 — неверно или не указано.
  Для типов: отказ парольной аутентификации; отсутствующее отношение;
  недостаточные права на объект; ошибка разрешения имени.
- Рекомендации: отдельно наличие проверки эффективной конфигурации/роли/объекта
  и проверки, способной различить оставшиеся гипотезы. Требуются цитаты и пояснение;
  простое количество рекомендаций не является качеством.
- Правильность ссылок и использование уже известных сведений — отдельные замечания.
- Входные/выходные токены, время генерации, достижение лимита и фактический обрыв.
- Наличие содержательного диагноза: отказ от ответа без использования явной ошибки
  не считается улучшением только из-за отсутствия причинных утверждений.

R оценивается по применимым тем же критериям; отсутствие развёрнутого текста или
ровно двух рекомендаций не штрафуется. Если правила не распознали ошибку, это
сохраняется как отсутствие диагностического результата, а не правильный диагноз.

Результаты разметки с участием ИИ обозначаются как предварительные.
Желательна независимая проверка вторым человеком. При её отсутствии это ограничение
указывается явно. По возможности оценщик получает анонимные идентификаторы ответов;
полную слепоту гарантировать нельзя, поскольку подсказки могут угадываться по тексту.

## 6. Агрегация

Единица содержательного сравнения — случай, а не seed. C01/C02 и C03/C04
дополнительно связаны общим типом симптомов; независимость всех шести не предполагается.
По каждому случаю показываются результаты трёх seed в L0 и L1 и результат R.

Сначала публикуется таблица парных исходов и неоднозначностей.
После согласования разметки вычисляются описательные доли ошибок по каждому случаю
и разности L1 минус L0. При неразрешённых метках показываются их числа и границы
возможной доли, без молчаливого исключения.
Для токенов и времени показываются отдельные значения и описательные сводки.

Шесть целенаправленно выбранных случаев не являются представительной выборкой.
Не заявлять статистическую значимость, промышленную точность или экономию времени
инженера. Более широкие выводы требуют расширения дизайна, а не увеличения числа seed.

## 7. Ошибки запуска и изменения

Не исключать ответ из-за плохого диагноза. Достижение лимита не является основанием
для выборочного увеличения бюджета или повторной генерации.
Сбой исполнения отмечается отдельно от содержательной ошибки модели.
Повтор после технического сбоя получает новый ID и связь с исходной попыткой;
журналы и незавершённые материалы сохраняются. Правило выбора результата — первая
технически завершённая попытка задания, а не лучший ответ.

При исправлении кода во время серии остановить сравнение, сохранить прежнюю версию
и определить новый полный блок сопоставимых запусков. Не смешивать версии молча.

## 8. Условия перехода к генерациям

1. Исследователь проверил и согласовал протокол.
2. Все включённые случаи технически проверены; команды и восстановление зафиксированы.
3. Входы, вопросы, правила, код, параметры и порядок запусков закреплены хешами.
4. Удалены только явно определённые до запуска секреты; диагностические сведения
   не отбираются по желаемому результату.
5. Техническая памятка и порядок работы со спорными метками согласованы.

До выполнения этих пунктов документ остаётся проектом. Основная серия не начата.
