# Протокол пилотного сравнения диагностического контекста

Дата: 22 октября 2026 года.
Статус: план до сравнительных запусков.

## Цель

Проверить, как добавление журналов базы данных и организация
наблюдений влияют на обоснованность диагностики локальной модели.

Это предварительный эксперимент на одном известном инциденте.
Первый ответ модели уже изучен. Протокол фиксируется до новых
сравнительных запусков, но не является независимой проверкой
на ранее неизвестном случае.

## Исходный инцидент

Контролируемая остановка PostgreSQL.
Идентификатор: 20261021T120747Z.
Момент диагностики: 2026-10-21T12:17:01Z.

Используются только наблюдения, доступные до этого момента.
Команды оператора и сведения о восстановлении модели не передаются.
Истинный сценарий хранится отдельно и используется при оценке.

## Варианты контекста

A — описание системы, проверки HTTP до и во время сбоя,
непосредственная ошибка подключения к db.
Соответствует наблюдениям E1, E4 и E5 первого запроса.

B — сведения из A и журнал остановки PostgreSQL.
Добавляются наблюдения E2 и E3.
Наблюдения сгруппированы по источникам.

C — те же сведения и идентификаторы наблюдений, что в B,
но события представлены в хронологическом порядке.

Во всех вариантах сохраняются одинаковые вопросы и инструкции.
В C не добавляются готовый диагноз и причинные пояснения.

Сравнение A и B оценивает добавление доказательств.
Сравнение B и C оценивает организацию одинаковых фактов.
Количество входных токенов фиксируется отдельно.

## Условия запусков

Модель: Qwen/Qwen3-1.7B без дообучения.
Ревизия: 70d244cc86ccca08cf5af4e1e306ecf908b1ad5e.
Режим: enable_thinking=False, dtype=bfloat16.
Параметры: do_sample=True, temperature=0.7, top_p=0.8,
top_k=20, max_new_tokens=768.

Для каждого варианта выполняются три запуска:
seed 42, 43 и 44. Всего девять новых запусков.

Одинаковые значения seed используются для всех вариантов.
Каждый запуск получает только свой запрос, без истории диалога.
Первый пилотный ответ сохраняется отдельно от новой серии.

## Правила оценки

Каждый критерий оценивается отдельно:
0 — неверно или отсутствует;
1 — частично правильно;
2 — правильно и без существенных противоречий.

1. Проблемный компонент
2 — указана недоступность зависимости БД для API;
1 — указана общая проблема подключения без локализации;
0 — выбран другой компонент без подтверждения.

2. Непосредственная ошибка
2 — названа ошибка разрешения имени db;
1 — названа только общая ошибка подключения;
0 — указана другая ошибка либо ответа нет.

3. Обоснованность объяснения
Для A:
2 — проблема доступа к БД установлена, но конкретная причина
не объявлена доказанной; остановка допустима как гипотеза.
Для B и C:
2 — остановка PostgreSQL связана с потерей доступа к БД,
при этом инициатор остановки не придуман.
1 — объяснение неполное либо содержит чрезмерно уверенный вывод.
0 — объяснение противоречит наблюдениям.

4. Точность использования наблюдений
2 — ссылки соответствуют утверждениям, коды HTTP и время
интерпретированы правильно;
1 — есть отдельная неточность при верном основном выводе;
0 — доказательства существенно искажены или не приведены.

5. Разделение фактов и неизвестного
2 — явно указано, что причина и инициатор остановки не установлены;
для A также не считается доказанным сам факт остановки.
1 — неопределённость обозначена неполно;
0 — неизвестные обстоятельства представлены как факты.

6. Дополнительные проверки
2 — предложены две конкретные, применимые и технически
корректные проверки, помогающие различить причины;
1 — полезна только одна проверка либо предложения слишком общие;
0 — полезных проверок нет или предложены некорректные действия.
Корректность названных команд проверяется отдельно по документации.

Для каждого балла сохраняются цитата из ответа и пояснение.
Одно утверждение может затрагивать несколько критериев;
это отмечается в комментарии к оценке.

## Дополнительные показатели

Отдельно фиксируются:
- неподтверждённые утверждения с цитатами;
- ошибочные ссылки на наблюдения;
- некорректные команды и рекомендации;
- число входных и выходных токенов;
- время генерации;
- достижение лимита ответа.

Гипотеза, явно обозначенная как гипотеза, не считается
выдуманным фактом только потому, что она не подтверждена.

При обрыве ответа по лимиту результат сохраняется с отметкой.
Нельзя выборочно увеличивать лимит только для неудачного варианта.

## Представление результатов

Сохраняются все ответы, включая неудачные.
Результаты показываются по каждому критерию и запуску.
Основной вывод не сводится к одному суммарному баллу.

Три запуска одного инцидента не считаются тремя независимыми
инцидентами. Результаты не используются для заявления
статистически подтверждённого преимущества или научной новизны.

После пилота схема уточняется и проверяется на новых инцидентах.
Все изменения протокола фиксируются отдельной версией.
